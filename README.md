# Visit API: Serverless Infrastructure-as-Code with AWS CDK

A hands-on project exploring infrastructure-as-code with the **AWS Cloud Development Kit (CDK)**. It defines a small serverless "visit counter" API, including its monitoring and alerting, entirely in TypeScript, and deploys it to AWS through CloudFormation.

## Architecture

```
Client ──► API Gateway (REST) ──► Lambda (Node.js 20) ──► DynamoDB
                                     │
                                     ▼
                          CloudWatch alarm (Lambda errors)
                                     │
                                     ▼
                              SNS topic ──► Email alert
```

| Component | Purpose |
|---|---|
| **API Gateway** | Public REST endpoint that proxies every request to the Lambda function |
| **Lambda** | Increments and returns a visit count for the requested path |
| **DynamoDB** | Stores visit counts (on-demand billing, keyed by page path) |
| **IAM** | Least-privilege read/write access from Lambda to the table, generated by CDK |
| **CloudWatch alarm** | Fires when the function records one or more errors in a minute |
| **SNS** | Sends an email notification when the alarm fires |

All of these resources are defined in [`lib/visit-api-stack.ts`](lib/visit-api-stack.ts). The function code is in [`lambda/index.mjs`](lambda/index.mjs).

## Prerequisites

- An AWS account and the AWS CLI configured (`aws configure`)
- Node.js 20 or later
- AWS CDK CLI: `npm install -g aws-cdk`

## Deploy

```bash
npm install
cdk bootstrap                               # one-time setup per account/region
cdk synth                                   # generate and validate the CloudFormation template
cdk deploy -c alertEmail=you@example.com    # alert email is passed as context, not hard-coded
```

After deploying:

1. Confirm the SNS subscription email that AWS sends you.
2. Note the `ApiUrl` value in the stack outputs.

## Try it

```bash
# Increment and return the visit count for /home
curl https://<api-id>.execute-api.<region>.amazonaws.com/prod/home
# {"page":"/home","visits":1}
```

## Test the alerting

The function includes a deliberate failure switch for testing monitoring:

```bash
curl "https://<api-id>.execute-api.<region>.amazonaws.com/prod/home?fail=true"
```

Within a few minutes, the `VisitFnErrors` alarm moves to **In alarm** in CloudWatch and an email alert is sent. The error and stack trace can be inspected in the function's CloudWatch Logs.

## Making changes

Infrastructure changes are made in code and reviewed before they are applied:

```bash
cdk diff      # preview exactly what will change
cdk deploy -c alertEmail=you@example.com
```

## Tear down

```bash
cdk destroy
```

The DynamoDB table uses `RemovalPolicy.DESTROY`, so it is deleted with the stack. This suits a sandbox only; production data stores would normally be retained.

## What I learned

- **Infrastructure as reviewable code.** About 50 lines of CDK synthesise into a much larger CloudFormation template, including IAM policies that would otherwise be written by hand. `cdk diff` gives a change review step before each deployment.
- **Least privilege by default.** `table.grantReadWriteData(fn)` generates a scoped IAM policy rather than broad permissions.
- **Monitoring belongs in the same code as the service.** Defining the alarm and its notification alongside the function means every environment deployed from this stack is monitored from day one.
- **Keep secrets and personal settings out of source.** The alert email is supplied at deploy time as CDK context.
